# Local homeowner case service

`case_service.py` connects the existing two-stage answer store to an authenticated HTTP API. It binds only to `127.0.0.1`. It is a local development component, not the deployed LEVEL GROUND customer portal.

## Access and operation

An operator creates a case with `AnswerStore.create_case(label)`, then calls `CaseAccess(store).issue(case_id, actor_id, role)`. Supported roles are `homeowner` and `reviewer`. Credentials use 32 random bytes, are stored only as SHA-256 hashes, default to a one-day lifetime and can be revoked using `CaseAccess.revoke(token)`. Actor identity is assigned by the operator, not accepted from an answer or review request. Possession of a credential authenticates access to that single case; this does not verify someone's legal identity.

Start from the repository with the supported Python environment:

```text
python levelground/case_service.py --database /absolute/path/to/cases.sqlite3 --port 5819
```

Every request supplies `Authorization: Bearer <credential>`. Do not put credentials in URLs. JSON writes also require `Content-Type: application/json` and a Content-Length. Case identity is derived from the credential. Do not copy a developer credential into reports, logs or source control.

| Route | Access | Behavior |
|---|---|---|
| GET `/api/case` | Both roles | Own case, both report stages, answer history and document inventory |
| GET `/api/reviewer-queue` | Reviewer | Current case's pending answers, document preparation, sheet coverage and measurement review tasks |
| POST `/api/evidence` | Both roles | Store `filename` and `content_base64`; returns an immutable `evidence:` reference |
| GET `/api/evidence/<id>` | Both roles | Download own-case original bytes after hash verification |
| POST `/api/answers` | Both roles | Append `report_id`, `question_id`, `text`, optional `evidence_refs` |
| GET `/api/reports/<id>` | Both roles | Current question status and complete report JSON; original report retained |
| GET `/api/reports/<id>/download` | Both roles | Offline HTML attachment with current saved answers and review status; verifies case ownership and evidence |
| POST `/api/reports` | Reviewer | Attach `report` generated by the existing report pipeline, stage `pre_bid` or `bid_gap` |
| POST `/api/reviews` | Reviewer | Review `report_id`, `answer_id`, `decision`, `rationale`, `evidence_refs` |
| POST `/api/bid-document-reviews` | Reviewer | Save an immutable, page-sourced bid document review against the current extraction |
| GET `/api/bid-document-reviews/<id>` | Reviewer | Read a source-verified document review within the case |
| GET `/api/bid-document-reviews/<id>/draft` | Reviewer | Generate an unpublished report from the latest document review |
| POST `/api/bid-package-draft` | Reviewer | Compare a governing builder bid with selected quote/addendum reviews; retain incorporation uncertainty, conflicting wording and separate totals |
| GET `/api/document-processing/<id>/bid-preparation` | Reviewer | Prepare source lines, topic suggestions, total candidates and an unpublished question draft from existing extraction |
| POST `/api/plan-workspaces` | Reviewer | Initialize a separate intake from a prepared plan's `source_reference` |
| GET `/api/plan-workspaces/<plan-sha256>` | Both roles | Own plan's safe intake/coverage status; no private defaults or filesystem paths |
| POST `/api/plan-workspaces/<plan-sha256>/measure` | Reviewer | Prepare native measurement candidates for the current reviewed sheet scope; accepts only `sheet_review_sha256` |
| GET `/api/plan-workspaces/<plan-sha256>/prebid-draft` | Reviewer | Generate an unpublished pre-bid report from current measurement rules and sheet review |

Answers remain homeowner-reported until a reviewer acts. A changed answer reopens the question. Resolving a question does not recalculate quantities or prices, rewrite findings, certify code compliance, or release an estimate. This API currently delivers the existing updated-report JSON; explicit finding narrative updates remain in the operator backend.

Uploads are stored as bytes, never executed or opened as active web content. Per-file maximum is 25 MiB. Evidence downloads use attachment disposition and nosniff. All API responses use no-store. Host/origin checks refuse other websites, and no cross-origin allowance is provided. Customer and reviewer credentials cannot retrieve another case's report, upload or answer history.

## Verified local scope

The reviewer queue supplies a `measurement_request` only when the selected upload has an approved sheet scope and no prepared draft. Its request body binds preparation to the sheet-review hash. The measurement endpoint rechecks case ownership, the original uploaded plan, frozen intake/profile/inventory hashes and the reviewed scope. Repeated requests reuse a completed current draft without rerunning the engine or rewriting files. Incomplete or stale output is preserved and requires inspection; the queue does not offer an automatic retry. Overlapping requests are serialized within the service. Successful preparation records the authenticated reviewer internally in `measurement_run.json` but exposes only safe status and candidate counts. No report is attached, price approved or estimate released. The endpoint does not create or approve the prerequisite sheet review.

## Local report download

The local portal offers **Download review** for the selected stage and report version. It retrieves an authenticated HTML attachment that can be read offline or printed through the user's browser. The copy includes original findings, quantities and unknowns, outstanding questions, latest saved answers, review decisions/rationales, evidence references and the source report hash. Unfinished in-page answers are excluded. Downloads do not modify the case, recalculate values or release an estimate. Changed answers reopen their questions in later copies. Closing the project suppresses a pending download.

The attachment uses the existing report template, removes external font requests and restricts scripts to the hashed renderer. Embedded JSON and displayed text are escaped; missing measurements remain unknown. Fifty-one LEVEL GROUND tests passed, including other-case and invalid-credential rejection, source/evidence tampering, answer revision and renderer escaping. Browser checks downloaded both synthetic stages and verified that the saved files contain only saved answers. The button layout was visually checked. ## Reviewed bid documents

### Combined bid and attachment review

`POST /api/bid-package-draft` takes `primary_review_id` and one to twenty `attachments`. Each attachment supplies `review_id`, `relationship` (`incorporated` or `unconfirmed`) and a source-based `rationale`. Identity comes from the reviewer credential. The primary must be a builder bid; attachments must be trade quotes or scope addenda. Duplicate documents, older reviews and other-case sources are rejected. The primary and incorporated attachments require complete document review. An unconfirmed attachment may remain partial but cannot establish builder scope.

The existing 36-topic engine combines only governing and incorporated wording. Separate per-document checks expose reviewed inclusion/exclusion differences even when a quote's incorporation is unknown. These differences generate source-linked findings and questions; no attachment automatically overrides the bid. Unconfirmed incorporation becomes a return-visit question. Homeowner answers do not change the relationship or approve a price.

`source_documents` retains each original hash, extraction hash, review hash, page list, relationship, rationale and document amount. `document_comparison` retains every topic for each document. `meta.primary_bid_total` preserves the selected primary amount while `meta.bid_total` and `meta.package_total` remain unknown until price reconciliation is implemented. Quote and addendum amounts are never summed into a home price. The source ledger is available in JSON; no new operator selection screen or document-amount table has been added to the homeowner preview.

Generation does not save a report or clear the queue. Before attaching a package through `/api/reports`, the server regenerates it under the authenticated reviewer and rejects stale or altered drafts. A changed attachment reopens the package's document work, including the primary; unconfirmed attachments stay pending even after a report is attached. Earlier reports and homeowner answers remain intact.

Eighty-three LEVEL GROUND tests passed, including eight package tests. The final package checks also cover malformed attachment lists, HTTP case/role boundaries, altered totals, revisions, return visits and preservation. The running local route validates input, refuses homeowner generation and preserves the existing case; a separate saved synthetic example compares a $300,000 primary bid excluding gutters with a $2,000 gutter quote. It flags the difference and leaves the package total unknown. See `outputs/levelground_bid_package_review`. This is software workflow validation, not independent estimating accuracy or complete contract review.

Before classifying a document manually, the reviewer can request `/api/document-processing/<evidence-id>/bid-preparation`. The queue includes this link for extracted documents, including those with blank pages requiring visual review. It prepares wording with one-based page/line references, related checklist topics, every extracted total candidate and a `machine_preparation` report with unconfirmed questions. The endpoint works with existing extractions without rewriting their hashes or changing previous reviews.

Preparation is computed on request, not published on upload. It retains non-matching lines as context and limits the editable batch to 1,000 nonblank lines; omitted counts/pages and unreadable pages remain explicit. A keyword suggestion never confirms scope, selects currency or chooses a total. Document type, reviewed pages, rationale and approvals remain unset in the supplied review template. The reviewer completes that template through the existing review endpoint; a current base-review ID preserves revision checks. Preparing a document neither clears its queue task nor attaches a homeowner report.

Preparation v2 also returns `clause_candidates` and `clause_detection_method`. The current clause method is `source_clause_candidates_v3`. It locates explicit English allowance, exclusion, owner-supply, extra-charge, price-change, quote-validity and referenced-document wording, including tariff pass-through language. Recognized adjacent headings such as EXCLUSIONS retain both the heading and item as evidence; page changes, blank-line gaps, neutral headings and new colon-ended headings stop that context. Literal source text, page/line references and matched character spans remain available. Dollar strings are retained as text, including unit rates and zero allowances; they are not converted into allowance totals or exposure estimates. At most seven grouped clause questions are added to the draft findings, while every candidate remains available in JSON. A passed validity date prompts follow-up; it does not establish supplier refusal or a price increase. No automatic expiration date is calculated from relative wording. The review template still has no approved scopes, currency or total. Existing source reviews and reports are not rewritten.

This is a lexical review aid, not complete contract interpretation. Wrapped clauses, tables, unfamiliar phrases, cross-page context and nuanced negation still require source review. Zero candidates is not a clean-bid verdict. Preparation identity includes the new method version so it differs from the earlier result for the same source. The current operator/homeowner delivery and independent accuracy gates remain open.

The operator can now connect extracted bid wording to the existing bid-gap report engine. POST `/api/bid-document-reviews` requires `evidence_id`, current `source_sha256` and `extraction_sha256`, `document_kind` (`builder_bid`, `trade_quote` or `scope_addendum`), `reviewed_pages`, `document_review_complete`, `rationale`, `base_review_id` and `lines`. Each line supplies a one-based `page`, literal `source_text`, optional `scope_status` (`included`, `excluded`, `unclear`), and `confirmed_scopes` using existing checklist titles. Reviewer identity comes from the credential. Use a null base on the first review; revisions must name the latest review ID.

An optional `total_candidate_index` selects a specific extracted total only after complete document review with confirmed `currency: "USD"`. Without selection, the total stays unknown. A trade quote or addendum retains its document total but cannot set the report's whole-home bid total. Partial reviews cannot establish scope inclusions, exclusions or a total. Source wording must occur on the reviewed page; hashes and latest-review identity are checked again when generating a draft.

GET `/api/bid-document-reviews/<id>/draft` returns a reviewer draft, not an attached or approved homeowner report. The operator separately reviews and attaches it through the existing report endpoint. A linked current review clears that document's queue task only when it uses the current checklist version; revising the review or expanding the checklist reopens it. Previous reports and homeowner answers remain in their existing history. The checklist now covers 36 trade and contract topics, but this step does not establish full trade completeness, plan quantities, attachment reconciliation, local requirements or price adequacy. Human source classification and report approval are still required; no automatic end-to-end homeowner review is claimed.

The shared report JSON includes `scope_checks`, stable topic IDs and `scope_checklist_version`. Each topic preserves its reviewed wording and distinguishes inclusion, exclusion, conflicting wording, unverified scope, unknown optional selection and an explicit intake exclusion. Keywords alone cannot confirm an omission. Source-confirmed inclusions leave the open-question list but remain in `scope_checks`; contract-process topics also require evidence to close. An explicit intake exclusion conflicts with related bid wording rather than hiding it. `complete_home_scope_review` remains false even when every checklist topic has a source confirmation. The current UI and HTML export still show findings/questions, rather than a separate table of all included scopes; the full ledger is available in the report JSON.

## Automatic document preparation

### Reviewer work queue

`GET /api/reviewer-queue` groups the authenticated case's work by reviewer, homeowner and document worker. It uses the latest report for each stage, retains historical versions in the case record, and includes only unresolved questions. A new answer requires review; an accepted answer leaves the queue until revised. Rejected or clarification-needed answers return to homeowner follow-up. No messages are sent automatically.

Documents with incomplete extraction require manual review. Extracted documents still require scope classification. Selected plan workspaces expose missing sheets, revision conflicts and remaining measurement review. Changed evidence or interrupted intake produces an explicit verification task rather than a healthy status. This endpoint changes no reports, answers, evidence or measurements. An empty queue does not prove estimate completeness or permit compliance.

Fifty-nine LEVEL GROUND tests passed, covering current report selection, answer revisions, preparation/manual-review transitions, altered sources, interrupted workspaces, role and case isolation. The live local case returned five reviewer tasks: two sample answers, one sample addendum, and the actual Burns plan's sheet and measurement tasks. Direct and HTTP results match. Reports, answers, document bytes and Roberts workbook were preserved; the temporary test credential was revoked. The homeowner UI does not yet display this operator queue, and operator assignment, work-time metrics and production delivery remain unfinished.

The server discovers uploaded evidence in SQLite and processes one document at a time in a background worker. Uploads saved immediately before an interruption are discovered on return. Work is claimed transactionally; a lost five-minute claim can be recovered, and the claim token prevents an older worker from replacing a newer result. Completed and manual-review results are not processed repeatedly.

`GET /api/document-processing/<evidence-id>` returns the authenticated case's extraction and its status. `/api/case` includes `processing_status` with each document. Original bytes and extracted results are hash checked on retrieval. The current portal does not yet display the extraction status or an operator review queue.

Supported preparation: native PDF text and UTF-8 text, up to 250 pages and two million extracted characters. Original uploads remain limited to 25 MiB. Page/line references and all labeled total candidates are preserved; totals remain unreviewed and currency is unconfirmed. No candidate is applied to a price, bid total or report automatically. Unsupported, encrypted, invalid and over-limit documents retain their originals and require manual review. Blank extracted pages are marked for visual/OCR review; text on a page does not establish that all drawings or annotations were captured.

Statuses are `queued`, `processing`, `text_extracted`, `needs_visual_review`, and `needs_manual_review`. Text extraction is preparation, not a complete document review. Public operation still needs stronger parser isolation/resource limits, scanning and the existing deployment/privacy controls.

## Reviewed trade quote and plan comparison

Reviewer-only POST `/api/trade-quote-draft` accepts `document_review_id`, `workspace_id`, the current trade `scope_sha256`, a source-review `rationale`, and `quote`. The quote contains supplier, issue/validity dates, evidence kind, `scope_items`, and `pricing_lines` using the shared quote-review format. Every scope and price line cites `evidence:<id>, page <n>` from the reviewed document; quantity-basis and measurement-adjustment references use the same format. Total, currency and source bytes come from the retained latest complete trade-document review, not client replacements.

The workspace must belong to the authenticated case and provide exactly the selected current scope. The response connects arithmetic, billing-basis, duplicate-package and required material/labor coverage checks to homeowner questions. It remains a single-trade reviewer draft, with no invented missing costs or whole-house price. It does not automatically publish a report. POST `/api/reports` regenerates this draft from the current sources before attachment, rejecting altered findings and outdated document/scope revisions. Attached questions use the existing homeowner answer workflow. A dedicated pricing-transcription UI remains unfinished; this integration is available through the local reviewer API, not a public autonomous service.
